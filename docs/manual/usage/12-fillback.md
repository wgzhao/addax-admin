# 补数回补

补数（也叫补采）用于把“应该采集但没有采集”的历史日期重新采集一遍。正常调度只负责当前业务周期；历史日期用补数处理。

## 入口

打开采集表详情页，切换到「补数」tab。

补数按采集表逐张提交：详情页只处理当前表。需要一次给多张表补数时，仍可在采集表列表勾选多张表后使用「补采数据」弹窗；两者最终都会生成相同的队列任务。

## 选择日期

补数日期从日历中选择，支持：

- **区间**：点选开始日期，再点选结束日期，然后点「添加」。
- **单日**：只点选一天，然后点「添加」。
- **多段不连续区间**：可以分多次添加，例如先加 `01-03 ~ 01-10`，再加单日 `01-13`。
- 已选区间以标签展示，可逐段删除或全部清空；重复日期会自动去重。

日期上限是**系统业务日期**（`BIZ_DATE`，受切日时间影响），不是自然时间的今天：

- 业务日期之后的日期在日历中不可选，后端也会拒绝提交。
- 业务日期通常就是上一个业务日，因此今天及以后的日期一般不可补。

单次提交最多 **20 天**（详情页只选一张表，所以是 20 个日期；列表页多选时是「表数 × 天数」不超过 20）。

## 提交与进度

点击「开始补数」后，每个「表 × 日期」会生成一条独立的队列任务，使用该日期作为任务业务日期。提交是异步的，页面不会等待采集结束。

提交成功后，进度面板每 3 秒刷新一次，直到所有日期进入终态：

| 状态                | 含义                                                        |
| ------------------- | ----------------------------------------------------------- |
| 等待中              | 已入队，等待调度                                            |
| 执行中              | Addax 子进程正在执行                                        |
| 成功                | 该日期采集完成                                              |
| 失败                | Addax 非零退出或执行异常，可展开查看错误                    |
| 已取消              | 被人工终止                                                  |
| 未入队 / 明细已清理 | 提交时已有同表同日期的等待/运行任务，或队列明细已被每日清理 |

批次整体状态包括：排队中、执行中、已完成、部分成功、失败、已取消、明细已清理。

页面会记住最近一次补数批次：刷新页面或重新进入 tab 时会恢复该批次的日期和进度。补数记录只保留「当前/最近批次」，每日队列清理会删除更早的终态明细；执行快照仍可在「执行快照」tab 查询。

## 时间变量

补数只改变本次任务的业务日期，不会修改系统全局业务日期，也不会影响正在运行的其它任务：

- `biz_*` 使用补数选择的日期。
- `curr_*` 使用该次补数生成任务内容时的真实日期时间。
- 补数任务按目标日期重新生成采集任务内容，所有日期变量在生成时即冻结为确定值，写入任务 JSON 后不再变化；全局 `BIZ_DATE` 保持不变。
- 补数不读取「采集任务配置」中手工编辑过的缓存内容。

因此补历史日期时，动态表名、过滤条件、目标分区和快照业务日期列都会按所选日期生成。每次补数执行前写出的 job 文件记录了该次实际使用的全部日期值，可直接用于排查。

## 支持的表

补数需要目标端有「日期维度」：

- HDFS 表：至少有一个 `BIZ_DATE` 类型的分区绑定。
- 关系型目标表：配置了快照业务日期列（`businessDateColumn`）。

以下表不支持补数，提交时会被跳过并记录风险日志：

- HDFS 非分区表。
- 未配置快照业务日期列的关系型目标表。

没有日期维度的表补多个日期会互相覆盖，因此平台直接拒绝，而不是产生重复数据。

## 增量过滤 `__max__<字段>` 的补数行为

过滤条件为 `__max__<字段>` 的表（例如 `__max__id`，关系型、MongoDB、Elasticsearch 源同理）在补数时，平台不会原样执行该条件，而是**按每个补数日期分别计算下界**：

```text
<字段> > 目标端「补数日期的前一个业务日」的最大值
```

目标端最大值按日期范围查找：HDFS 表查对应 `BIZ_DATE` 分区，关系型目标查快照业务日期列。

以补数 `2026-08-08`、`2026-08-10`、`2026-08-12` 为例：

| 补数日期     | 自然日下界   | 工作日/交易日下界（08-08 周六、08-09 周日） |
| ------------ | ------------ | ------------------------------------------- |
| `2026-08-08` | `2026-08-07` | `2026-08-07`                                |
| `2026-08-10` | `2026-08-09` | `2026-08-07`                                |
| `2026-08-12` | `2026-08-11` | `2026-08-11`                                |

例如补 `2026-08-10`（自然日）时，实际执行的过滤是：

```sql
id > MAX(目标表在 2026-08-09 分区/快照中的 id)
```

需要明确的预期：

- **只有下界，没有上界。** 补历史日期时，源端已经存在该日期之后的数据，这些数据也会被读取，并写入补数日期对应的分区/快照（关系型目标还会给它们打上补数日期的业务日期）。例如补 `08-08` 会把 `08-08` 之后新增的数据一起写进 `08-08`。只使用 `__max__<字段>` 的表不适合补历史。
- **前一个业务日没有目标数据时会退化为全表读。** 取不到最大值时平台回退为 `1=1` 并记录风险日志（「无法获取目标表…最大值，使用默认过滤 `1=1`」）。补 `08-10` 时如果 `08-09` 从未采集，就会发生这种情况。
- **连续日期补数有先后依赖。** 补 `08-08`、`08-09` 时，`08-09` 的下界来自 `08-08` 的目标数据；如果 `08-08` 还没跑完就派出 `08-09`，可能取不到值而全表读。
- **HDFS 目标的分区不存在或为空时**，平台可能复用之前缓存的增量最大值；该缓存不区分日期，下界可能来自另一天。
- **工作日历下，非业务日与之后第一个业务日的下界相同。** 例如周六的补数与周一补数都使用周五；补数接口不会拒绝非业务日。

因此：

- `__max__<字段>` 适合**连续每日采集**；历史回补请使用带日期条件的普通过滤（例如 `dt='${biz_date_dash}'`），不要依赖 `__max__`。
- 如果必须补 `__max__` 表，先确认「补数日期的前一个业务日」的目标分区/快照存在，避免全表读，并在执行后核对目标数据的时间范围。

## 限制与注意事项

- **同表同日期去重**：如果该表在该日期已经有等待中或运行中的任务（自动调度、手工执行或上一次补数），本次补数会跳过该日期，不会并行执行两条相同任务。
- **全部跳过**：如果本次提交的日期全部被去重，队列里不会留下该批次的行；页面会显示提交结果，但刷新后无法恢复该批次的进度。
- **明细清理**：队列的终态明细会随每日清理删除；超过保留窗口的补数批次不会再出现在补数 tab 中，历史执行结果请查「执行快照」和「采集日志」。
- **手工编辑的任务内容**：补数按系统模板和当前采集定义重新生成，不包含在「采集任务配置」tab 里手工改过的 job。
- **取消**：补数 tab 不提供按批次取消。现有「终止」按采集表生效，会同时停止该表正在运行的自动调度和补数任务，请谨慎使用。
- **补数与自动调度**：补数不会改变采集表的停采/退役状态，也不会修改调度时间。
- **增量过滤表**：过滤条件为 `__max__<字段>` 的表补数只有下界、没有上界，可能把后续日期的数据写入补数日期；详见上文「增量过滤 `__max__<字段>` 的补数行为」。

## 常见问题

**为什么某些日期在日历里点不了？**

日期超过系统业务日期（`BIZ_DATE`）时会被禁用。请先确认「系统配置」里的切日时间和业务日期。

**为什么提交后进度显示“未入队”？**

该日期已经存在等待中或运行中的同表任务，队列按「表 + 业务日期」去重。等原任务结束后再提交即可。

**为什么补数成功但目标没有数据？**

先确认该表是否属于增量采集，且目标端的快照业务日期列、分区绑定是否正确；再检查「采集日志」中的 Addax 输出。没有日期维度的表会被直接跳过。

**为什么 `__max__id` 的补数把后面几天的数据也写进来了？**

`__max__` 只提供「`id` 大于补数日期前一个业务日的最大值」这个下界，没有上界；补历史日期时源端已经存在后续数据。详见上文「增量过滤 `__max__<字段>` 的补数行为」。只使用 `__max__` 的表不适合补历史，请改用带日期条件的普通过滤。

**补数会修改当前业务日期或影响今天的自动调度吗？**

不会。补数只把目标日期写入本次任务，并重新生成该任务的采集内容；全局业务日期、调度器和其它任务都不受影响。
