# Addax Admin 产品路线图

> 本文是产品层面的规划，与 `CONTEXT.md`（术语）、`docs/adr/`（架构决策）配合使用。
> 状态：P0 启动中（2026-11-14）。

## 定位

面向 Addax 离线引擎的 **T+1 ODS 层数据落地** 管理与运维控制台。

- 主打 **EL**（抽取 + 加载），不扩展 T（转换）。
- 不做 **CDC / 实时同步**。
- 不负责 EDW / ADW / ADS（下游数仓层），但以「就绪信号外发」与下游协作。

我们要赢的战场不是「数据集成全家桶」，而是 **ODS 落地的可信、可治理、可运维**。

## 明确不做（边界）

| 项 | 说明 |
|---|---|
| CDC / 实时同步 | 出局，离线 T+1 定位 |
| 自建转换 / T 引擎 | 出局，T 交给下游 Hive/dbt/Spark |
| 通用数据质量平台 | 不做，只做 ODS 特化 DQ |
| 完整任务编排 DAG | ODS 内部表无依赖，保留源级 `prerequisite`/`preScript` + 就绪信号外发 |
| 连接器广度扩张 | 国产库走 MySQL/PG 协议、Doris/ClickHouse 已支持；仅剩 Doris 写入抽离 |

## 已具备（底座，差距都长在它上面）

采集定义/路由/退役生命周期、目标契约 + 显式字段映射、表结构演化、批量建表、动态表名、增量过滤、补数回补、执行快照、失败事实/错误中心、多渠道告警中心、多节点 HA（Redis 选主 + DB 租约 + 权重）、三角色 + 源级授权、审计、交易日历、经营总览。

## P0 详情

### 1. 数据对账

- **目标**：证明「数据对没对」——源/目标行数（及后续 checksum）是否一致。
- **范围（MVP）**：RDBMS 源 → RDBMS / Hive 目标；行数对账；可配容差；自动（采集成功后）+ 手动（指定 tid+biz_date）。
- **非目标**：MongoDB/ES 源、列级 checksum、逐行抽样（后续版本）。
- **结果去向**：新表 `etl_reconcile`；差异 → 失败事实（新阶段 `RECONCILE`）→ 告警中心。

### 2. 字段级血缘

- **目标**：全局字段搜索 + 表级/字段级血缘图。
- **数据来源**：`etl_column_mapping(source_column_name → target_column_name)` + `etl_table` 关联源/目标，纯 join 零迁移。
- **MVP**：字段搜索（来源→去向列表）、表详情血缘面板、反向影响分析。

### 3. ODS 主动数据质量

- **目标**：落地数据「全不全 / 重不重」的主动断言。
- **规则（MVP）**：行数波动（相对基线）、主键唯一 / 重复、关键字段空值率、业务日期缺失。
- **复用**：告警中心 + 错误中心 + 失败事实。

## 演进原则

- 先「对账」再「血缘 / 质量」——先证明数据可信，再谈数据从哪来、全不全。
- 每个能力都长在现有底座（失败事实、告警、字段映射、快照）之上，不另起炉灶。
- 每项功能先写 ADR 定语义与边界，再实现。
