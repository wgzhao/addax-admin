# Record collection failures as durable, inspectable facts

Failure evidence is currently spread across four stores with different lifecycles, and one of them
is not written on many failure paths at all. The table list exposes a single icon that calls
`GET /tasks/{tid}/last-error`; that endpoint reads the newest failed `etl_jour` row and otherwise
returns the literal string `No error message found for the given table ID`, which users read as the
failure reason. There is no failure history, no link from a failure to the execution and raw log
that produced it, and no way to clear failure history independently of raw logs.

This ADR makes one failure fact per failed operation a first-class record.

## Why the current stores cannot answer the question

| Store | What it holds | Why it is not a failure history |
| --- | --- | --- |
| `etl_jour` | operation journal, one row per step | only paths that call `failJour`; `error_msg` truncated to 500 chars; no log link; never purged; mixes schema, partition and collect failures under one table without a stage query |
| `etl_execution` | immutable run snapshot | one row per attempt, but `error_message` is a short run-level summary and only failures after an execution started are recorded |
| `addax_log` | raw addax output | only written after the addax process starts; 180-day retention; no extracted error, so reading it is a manual full-text scan |
| `etl_job_queue.last_error` / `alert_event.payload` | queue and alerting state | final-attempt oriented, scoped to retry or delivery, not a diagnostic record |

Specific gaps:

- `JobContentService.updateJob` has no failure branch. An exception propagates without a journal
  row while the table may already be in a failed or update-schema state.
- `TableService.refreshTableResources` can fail a table on target contracts or column sync without
  a collection attempt, so no `etl_jour` `COLLECT` row exists.
- A stale `E`/`U` state (manual change, pre-deploy leftovers, an admin JVM crash between journal
  writes) has no error text at all.
- Raw logs expire before `etl_jour`, so the evidence trail can silently lose its deepest layer.

## Decision

Add an append-only `etl_failure` table. One row is one observed failure of one operation on one
collection definition. It is the single read model for the status icon, the table detail history and
the global error center, and the single write target for failure recording.

Rejected alternatives:

- **Extend `etl_jour`.** The journal is an operation log; error rows have a different retention
  (shorter than execution history, longer than raw logs), a different access shape (paged, filtered
  by stage/category) and extra evidence columns. Overloading it would repeat the current confusion
  where an old schema error is presented as the collection error. Cleanup would also delete
  operation history that is not an error.
- **Read `addax_log` on demand.** Logs are absent for schema/target/job-generation failures and are
  purged independently, and scanning a hundreds-of-megabytes text column to find a reason is not a
  query plan.
- **Reuse `alert_event`.** Alerting only publishes final failures, groups by event key, and owns
  open/resolved state. Diagnostic evidence must include every failed attempt and every stage.

### Schema

```sql
create table if not exists public.etl_failure (
    id             bigint generated by default as identity primary key,
    tid            bigint not null,
    execution_id   bigint,
    job_queue_id   bigint,
    log_id         bigint,              -- addax_log.id, deliberately no FK
    log_name       varchar(255),        -- addax output file name, disk fallback
    occurred_at    timestamp without time zone not null default current_timestamp,
    stage          varchar(32) not null,
    category       varchar(32) not null default 'UNKNOWN',
    error_class    varchar(200),
    error_code     varchar(64),
    summary        varchar(1000) not null,
    detail         text,
    fingerprint    varchar(64) not null,
    attempt_no     integer,
    max_attempts   integer,
    final_attempt  boolean not null default true,
    run_type       varchar(16),         -- NORMAL / FILLBACK
    biz_date       date,
    source_id      integer,
    source_db      varchar(64),
    source_table   varchar(255),
    target_db      varchar(64),
    target_table   varchar(255),
    legacy_jour_id bigint               -- backfill idempotency only
);

create index if not exists idx_etl_failure_tid_time
    on public.etl_failure (tid, occurred_at desc, id desc);
create index if not exists idx_etl_failure_time
    on public.etl_failure (occurred_at desc);
create index if not exists idx_etl_failure_fingerprint
    on public.etl_failure (fingerprint, occurred_at desc);
create index if not exists idx_etl_failure_execution
    on public.etl_failure (execution_id);
create unique index if not exists uk_etl_failure_legacy_jour
    on public.etl_failure (legacy_jour_id);
create unique index if not exists uk_etl_failure_attempt
    on public.etl_failure (execution_id, stage, fingerprint)
    where execution_id is not null;
```

Notes:

- `log_id` has no foreign key on purpose. Raw logs are purged by retention; a failure must survive
  that purge and report `log purged` instead of a foreign-key error or a cascade that erases the
  failure.
- `uk_etl_failure_attempt` makes recording idempotent at the attempt level: the same failure cannot
  be inserted twice by two catch layers of the same execution. Different attempts have different
  `execution_id`, so retries remain separate occurrences.
- `legacy_jour_id` is populated only by the one-time backfill and keeps that backfill idempotent.
- Identity columns (`source_id`, `source_db`, `source_table`, `target_db`, `target_table`) are copied
  from the execution or table view so a fact stays readable without joining a mutable view. The same
  pattern already exists on `etl_execution`.
- `detail` holds the exception message and stack excerpt, capped at 64 KiB. The raw addax log is never
  copied here.

### Stages

`stage` is the step that failed, not the table status:

| Stage | Meaning | Source |
| --- | --- | --- |
| `PREPARE` | target preparation before the run | `prepareBeforeRun` false |
| `SOURCE_SCHEMA` | source columns could not be fetched | `ColumnService` |
| `TARGET_SCHEMA` | target table DDL/contract failed | target adapters, contract check |
| `PARTITION` | target partition missing or creation failed | `HdfsTargetAdapter` |
| `JOB_TEMPLATE` | job content generation failed | `JobContentService` |
| `COLLECT` | addax process failed, timed out or was killed | `TaskQueueManagerV2Impl` |
| `QUEUE` | retries exhausted outside a single process | queue manager |
| `RECOVERY` | an abandoned running execution was reconciled | startup recovery |

Legacy `JourKind` values map onto these stages; `FILLBACK` is a `run_type`, not a stage.

### Categories

`category` is a display and filtering aid, not a decision input. Conservative rules, first match
wins, default `UNKNOWN`:

`OOM`, `TIMEOUT`, `AUTH`, `TABLE_NOT_FOUND`, `NETWORK`, `DISK`, `CONTRACT`, `DATA`, `PROCESS`,
`UNKNOWN`.

The raw `summary` and `detail` are always preserved; classification never rewrites or hides them.

### Fingerprint

`fingerprint = sha256(tid | stage | error_class | normalized summary)`. Normalization strips ANSI
escapes, NUL bytes, collapses whitespace and trailing punctuation. It groups repeated occurrences for
the "same error N times" view. It is deliberately conservative: grouping two distinct errors is worse
than failing to group two similar ones.

## Write path

`FailureRecorder` is the only writer. It runs in `REQUIRES_NEW` and swallows its own exceptions:
recording must never change a collection outcome or roll back the caller.

`EtlJourService.failJour` gains an evidence-aware overload and delegates to the recorder, so every
existing `failJour` call site produces a fact without touching its logic. `executeAddax` passes the
log id, exit code and attempt context through the same overload instead of mutating `EtlJour` fields
directly.

Coverage matrix to close during implementation:

| Failure | Current evidence | Required change |
| --- | --- | --- |
| addax non-zero / timeout / SIGKILL | `etl_jour` + log | record with `log_id`, exit code, stage `COLLECT` |
| addax launch `IOException` | `etl_jour`, no log | record stage `COLLECT`, code `NO_LOG` |
| contract blocked | execution finished, no failure row | record stage `TARGET_SCHEMA` |
| target `prepareBeforeRun` false | execution finished | record stage `PREPARE` |
| job template missing / exception | execution finished or nothing | record stage `JOB_TEMPLATE`; add catch in `JobContentService.updateJob` |
| source column fetch failure | `etl_jour` `UPDATE_COLUMN` | record stage `SOURCE_SCHEMA` |
| target DDL / partition failure | `etl_jour` `UPDATE_TABLE`/`PARTITION` | record stage `TARGET_SCHEMA`/`PARTITION` |
| queue retries exhausted | `etl_job_queue.last_error` | record stage `QUEUE` with final attempt |
| admin JVM dies mid-run | table stuck in `R`, no fact | follow-up: startup reconciliation fails the stale execution and records stage `RECOVERY` |

Extract the addax error summarizer from `TaskQueueManagerV2Impl` into a shared utility so the
recorder and the existing result message use one implementation.

## Read surfaces

```
GET  /failures?tid&sourceId&stage&category&from&to&q&finalOnly&page&pageSize
GET  /failures?groupBy=fingerprint             -> aggregated repeats
GET  /failures/latest?tids=1,2,3               -> batch, cap 200
GET  /failures/tables/{tid}/latest
GET  /failures/{id}
GET  /log/addax/{logId}/content                -> existing raw log endpoint
POST /failures/cleanup {before, tid?, sourceId?, stage?, dryRun}
GET  /failures/stats?from&to
```

`latest` returns a typed answer instead of a bare string:

```json
{
  "available": false,
  "reason": "NO_EVIDENCE_FOR_STATE",
  "failure": null,
  "occurrences": { "count": 0, "firstSeenAt": null, "lastSeenAt": null },
  "evidence": { "detail": "available", "log": "missing", "execution": "missing" },
  "hint": "状态为失败但无故障记录，可能是部署前遗留状态或状态被手工修改。"
}
```

`reason` values: `NO_FAILURE`, `NO_EVIDENCE_FOR_STATE`, `PURGED`. `evidence.detail` and
`evidence.log` values: `available`, `purged`, `missing`, `restricted`; `evidence.execution` is
`available` or `missing`. This is the fix for the current misleading English string: every "nothing
to show" case now has a distinct cause and an explicit next step.

Authorization:

- failure summary, stage, time and attempt: any authenticated reader, matching the dashboard's
  existing `last_error` exposure;
- `detail` stack excerpt and raw log: `OPERATE` on the source, matching the existing rule that raw
  logs and rendered job JSON are operational reads;
- cleanup: `admin` only, and audited.

The old `GET /tasks/{tid}/last-error` stays for one release, reimplemented over the latest
`COLLECT`-stage fact. The frontend stops using it immediately.

## UI

1. **Table list status icon.** Keep the icon for `E`/`U` and open a right-side drawer instead of the
   current one-line popover. The drawer shows stage, attempt `x/y`, business date, summary, occurrence
   count for the same fingerprint, buttons for raw log / execution snapshot / full history, and the
   typed empty states above. The icon is only rendered for accounts that can operate the source.
   Failure data for visible rows is fetched lazily on click; no N+1 request per row.
2. **Table detail tab "失败记录".** Paged history for the table: time, stage, attempt, category,
   summary, execution and log links, filters by stage/date. Visible to readers; detail and log links
   show the restricted state for non-operators.
3. **Global 错误中心.** New page under system management: filters (source, table, stage, category,
   time range, keyword, final-only), detail/aggregate mode (by fingerprint with count and first/last
   seen), CSV export, and the cleanup dialog. Row click opens the same drawer.
4. **Log tab.** When opened from a failure, preselect the log by `execution_id` instead of the newest
   five entries.

## Retention and cleanup

Three independent lifecycles, by design:

| Fact | Default retention | Owner |
| --- | --- | --- |
| raw addax log (`addax_log`) | 180 days (`ADDAX_LOG_RETENTION_DAYS`) | existing scheduled purge |
| failure fact (`etl_failure`) | 365 days (`COLLECTION_FAILURE_RETENTION_DAYS`, minimum 30) | new scheduled purge |
| execution / journal facts | never auto-purged in this phase | unchanged |

Cleanup rules:

- only by cutoff date plus optional `tid`/`sourceId`/`stage`; there is no "clear all" button;
- `dryRun` returns matched counts (by month and stage) before deletion;
- deletion runs in batches of 10,000 to avoid long locks;
- cleanup deletes failure facts only. It never deletes raw logs or executions;
- every cleanup writes an audit event `COLLECTION_FAILURES_CLEANED` with actor, cutoff, scope and
  deleted count.

A log purge must never make a failure disappear. The UI reports `log purged` and keeps the summary.

## Migration and backfill

- DDL is added to `SchemaInitializer` with `create table if not exists` and matching indexes;
  `scripts/schema.sql` is regenerated.
- A one-time backfill imports failed `etl_jour` rows from the last retention window:
  `stage` from `kind`, `summary = left(error_msg, 1000)`, `detail = error_msg`,
  `error_class = 'LEGACY_JOUR'`, `legacy_jour_id = etl_jour.id`, `final_attempt = true`.
  It uses `on conflict (legacy_jour_id) do nothing` and is guarded by a marker row in a new
  `app_migration(name, applied_at)` table so a later cleanup cannot resurrect purged history.
- Pre-deploy preflight failures were never visible and are not reconstructed; the drawer reports
  them through `NO_EVIDENCE_FOR_STATE`.
- `scripts/demo/seed.sql` gains `etl_failure` rows for the seeded failing tables so the demo and the
  error center stay coherent.

## Consequences

- One extra row per failed operation, roughly 1 KB, bounded by retention. Write cost is negligible
  next to starting an addax process.
- Recording is a best-effort dual write. A recorder failure loses diagnostic evidence but does not
  change the collection result; it is logged to the application log and is a candidate for an
  operational alert later.
- Failure facts outlive raw logs and are destroyed only by explicit cleanup.
- The classifier and fingerprint are heuristics. They must never be used to suppress, rewrite or
  auto-resolve a failure.
- `etl_jour` remains the operation journal. Do not add more error semantics to it.

## Out of scope

- An incident state machine (acknowledge/ignore/resolve). `alert_event` already owns open/resolved
  alert state; duplicating it in the failure store would create two truths.
- Failures not attributable to a collection table (scheduler-wide, source-wide). They stay in the
  application log and alerting until a scoped failure subject exists.
- Stale-execution reconciliation (the `RECOVERY` stage). The stage constant exists so the UI can
  render it, but detecting abandoned `running` executions without racing a legitimate long run
  needs its own lease-aware design.
- Purging `etl_execution` or `etl_jour`.
- Automatic remediation of known categories. Categories carry hints only; operators still decide.
- Rewriting the dashboard's fail-top query. It counts failed collection journeys, while failure facts
  also include schema, partition and contract failures; swapping the source would silently change
  what the chart measures.
