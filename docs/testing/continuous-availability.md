# 连续可用性测试：采集进行中重启后端

本报告记录 Addax Admin 在「采集正在执行时重启后端服务」这一故障场景下的实际表现，作为版本能力的公开基线。测试在单节点测试环境完成，主机名、地址、账号和业务表名已脱敏，行数与耗时保留原始观测值。

- 测试日期：2026-11-22
- 被测版本：`4.7.1-SNAPSHOT`
- 重启方式：`bin/service.sh stop` + `start`（SIGTERM 优雅重启），以及 `kill -9` 强制终止

## 结论

| 场景 | 中断时状态 | 结果 |
| --- | --- | --- |
| 多表采集源（11 张表）采集中重启 | 10 张执行中、1 张排队 | 11/11 自动重试后成功，目标端行数与源端完全一致 |
| 单表采集中重启 | 1 张执行中 | 自动重试后成功，33.9 万行/269MB 与源端一致 |
| 单表采集中 `kill -9` 强杀 | 1 张执行中 | 子进程被包装器清理，租约到期后自动重试成功，数据一致 |
| 多表采集源（11 张表）采集中 `kill -9` 强杀 | 10 张执行中、1 张排队 | 10 个子进程全部清理，租约到期后 10 张全部自动重试成功，数据一致 |

关键保证：

- 重启时所有正在运行的采集子进程立即终止，**没有孤儿进程继续写目标端**。
- 被中断的表作为新的执行尝试自动重投，**不需要人工干预**。
- 没有重复写入、没有丢数；同一业务日期的目标数据最终与源端一致。
- 重启后服务约 8–10 秒恢复可用，主节点约 10 秒内恢复调度。
- 这组负载下，从重启到全部表补采完成约 **1–1.5 分钟**。

## 测试环境与数据

- 单节点部署，平台自身元数据库为 PostgreSQL，调度协调使用 Redis。
- 采集源：关系型数据库（MySQL）与文档数据库（MongoDB）。
- 目标端：关系型数据库（MySQL）与 HDFS/Hive（ORC，按业务日期分区）。
- 场景 A 数据量约 36.3 万行，分布在 11 张表；场景 B 为 33.9 万行、269MB。
- 测试前目标端当日分区为空，便于用目标端实际行数直接判定成败。

## 判定方式

1. 手工触发采集，确认对应 Addax 子进程已启动。
2. 重启后端，记录停机时队列状态与残留进程。
3. 重启后不做任何人工操作，等待队列自然收敛。
4. 通过以下事实交叉验证：
   - 队列终态（全部 `completed`，无 `pending`/`running` 残留）；
   - 采集执行记录（中断尝试为 `failed: Interrupted`，重试尝试为 `succeeded`）；
   - 采集统计（记录数、错误数）；
   - 目标端实际行数（关系型直接 `count(*)`；Hive 按当日分区 `count(*)`）。

## 场景 A：多表采集源采集中重启

采集源下 11 张表同时触发，其中 5 张写关系型目标、6 张写 Hive 目标。

时间线（均在同一次测试内）：

| 时刻 | 事件 |
| --- | --- |
| T+0s | 提交 11 张表，全部入队 |
| T+6s | 10 张执行中、1 张排队，Addax 进程已拉起 |
| T+8s | 重启后端；正在执行的子进程全部终止，残留 0 |
| T+9s | 队列中 10 条记录转为 `Interrupted` 并进入 30 秒退避，1 条排队记录等待重启后派发 |
| T+12s | 新进程启动 |
| T+18s | 本节点重新成为 master，恢复调度 |
| T+39s | 退避结束，被中断的表自动重投 |
| T+87s | 全部 11 张表补采完成 |

## 场景 B：单表采集中重启

被测表为文档数据库到 HDFS/Hive 的采集，单次采集约 33.9 万行、269MB。

| 时刻 | 事件 |
| --- | --- |
| T+0s | 提交单表采集 |
| T+2s | Addax 子进程已启动，采集进行中 |
| T+7s | 重启后端；子进程终止，队列记录进入 30 秒退避 |
| T+10s | 新进程启动 |
| T+16s | 本节点恢复 master |
| T+39s | 自动重投并开始补采 |
| T+64s | 补采完成 |

结果：33.9 万行、269MB、0 错误；目标 Hive 当日分区行数 338,959，与源端一致。中断的第一次尝试记录为 `failed: Interrupted`，第二次尝试 `succeeded`，没有遗留「永远运行中」的执行记录。

## 场景 C：`kill -9` 强杀进程

强杀没有停机钩子，恢复完全依赖进程包装器的孤儿清理和队列租约。单表与多表各测一次。

### 单表

被测表同场景 B。

| 时刻（相对强杀） | 事件 |
| --- | --- |
| T-7s | 采集已启动，Addax 子进程运行中 |
| T+0s | `kill -9` 后端进程 |
| T+9s | 包装器发现父进程消失，Addax 子进程全部终止，无残留写入 |
| T+12s | 新进程启动，随后清理上一实例遗留的租约心跳文件 |
| T+38s | 在 master 锁 TTL 到期后恢复 master（强杀无法主动释放锁） |
| T+1m55s | 队列行租约到期，被回收；同一时刻孤儿执行记录被标记为失败 |
| T+2m25s | 自动重投并完成补采 |

结果：目标 Hive 当日分区 338,959 行，与源端一致；0 错误；第一次执行记录被回收逻辑标记为 `failed: Interrupted`，第二次成功；无遗留 `running` 执行、无残留子进程、无重复写入。

### 多表（11 张表）

采集源同场景 A，强杀时 10 张正在执行、1 张排队。

| 时刻（相对强杀） | 事件 |
| --- | --- |
| T+0s | `kill -9` 后端进程 |
| T+2s | 9 个 Addax 包装器仍在收尾，3 秒后剩余 3 个 |
| T+9s | 全部包装器与 Addax 子进程消失；新实例随后清理 10 个遗留租约文件 |
| T+13s | 新进程启动 |
| T+38s | 恢复 master（锁 TTL 到期），排队中的第 11 张表立即补采 |
| T+2m0s | 10 条租约到期，队列行批量回收；同一时刻 10 条孤儿执行记录被标记失败 |
| T+2m43s | 10 张表自动重投并全部完成 |

结果：11/11 成功，共 362,956 行；目标端（关系型 5 张 + Hive 6 张）逐表行数与源端一致；10 条执行记录被对账为 `failed: Interrupted` 后重试成功，0 遗留 `running` 执行、0 残留进程、0 重复写入。

强杀路径的恢复时间由最长租约（120 秒）决定，明显慢于优雅重启的 30 秒退避，但单表和多表都不需要任何人工操作。

## 数据一致性说明

- **HDFS/Hive 目标**：扫描结束后先写临时目录，完成后再移动到正式分区，然后删除临时目录。中断时旧分区保持完整，重试成功后整分区替换，不存在半成品分区。
- **关系型目标**：`overwrite` 映射为按主键的 `REPLACE INTO`，中断窗口内目标表可能是旧数据与部分新数据的混合，重试完成后恢复完整；按主键写入保证重试幂等。
- **并发双写防护**：队列行租约、进程包装器的父进程存活检查与租约心跳共同保证旧进程先退出、后一次执行才可能开始；本次测试中每次重启后均确认旧 Addax 进程为零。
- **失败事实与告警**：中断尝试会记录一条非最终失败事实（`Interrupted`），最终尝试成功时不会产生失败告警，也不会触发重复告警。

## 恢复时间模型

| 阶段 | 优雅重启 | `kill -9` |
| --- | --- | --- |
| 服务启动到健康检查通过 | 8–10 秒 | 8–10 秒 |
| 被中断的 Addax 子进程退出 | 立即 | 约 10 秒内（包装器轮询） |
| 重新成为 master | 约 10 秒 | 最长约 30 秒（锁 TTL） |
| 被中断表的再次投递 | 30 秒退避 | 最长约 120 秒（租约到期） |
| 本组负载从重启到全部完成 | 1–1.5 分钟 | 约 2.5–3 分钟（多表实测 2 分 43 秒） |

同一「采集表 × 业务日期」的重试次数受 `retry_cnt` 约束（默认 3）。本场景中一次重启消耗一次尝试；如果在同一次运行内连续多次重启，可能耗尽重试次数，该表当日会被标记失败并需要人工重试或补数。

## 边界与未覆盖项

- 已验证优雅重启（SIGTERM）与 `kill -9`。OOM、断电等场景与 `kill -9` 走同一条恢复路径（租约过期 + 包装器孤儿清理），未单独复测。
- 单节点环境，未覆盖双节点主备切换期间的重启行为。
- 测试期间源端数据保持静态，未覆盖源表并发写入导致的快照差异。
- 关系型目标在中断窗口内可能短暂出现新旧数据混合，HDFS 分区则保持旧版本直到替换完成；下游读取需接受这一窗口。
- 测试数据规模为数十万行，未覆盖超大表（数小时级）采集中的重启。
- 被中断的 HDFS 写入会在分区目录下留下隐藏临时目录（本次三次中断各留下 1 个，实测均小于 1KB）；不进入 Hive 查询，但需要在运维上定期清理。
